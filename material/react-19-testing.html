🛡️ ErrorBoundary + use()

🚨 Cargar promesas y capturar errores asíncronos

use(promise) lee una promesa durante el render. Si está pendiente, el componente suspende y Suspense muestra su fallback. Si la promesa se rechaza, el error se lanza durante el render y lo captura el ErrorBoundary más cercano.

React 18: suspense, error manual y re-throw

React 18 

// version-18/UserProfile.tsx
const UserProfileContent = lazy(() => import("./UserProfileContent"));

export function UserProfile({ fail }: { fail: boolean }) {
  const userId = getUserId(fail);

  return (
    <ErrorBoundary key={String(userId)} message="No se pudo cargar el usuario.">
      <Suspense fallback={<Spinner />}>
        <UserProfileContent userId={userId} />
      </Suspense>
    </ErrorBoundary>
  );
}

// version-18/UserProfileContent.tsx
export default function UserProfileContent({ userId }: { userId: number }) {
  const [user, setUser] = useState<User | null>(null);
  const [error, setError] = useState<Error | null>(null);

  useEffect(() => {
    const fetchUser = async () => {
      setError(null);

      try {
        setUser(await userApi.getById(userId));
      } catch (err) {
        setError(new Error(getErrorMessage(err, "Error al cargar")));
      } 
    };

    void fetchUser();
  }, [userId]);

  // ❌ El boundary no ve este error si solo lo mostramos en pantalla.
  // Lo relanzamos durante el render para que sí lo capture.
  if (error) throw error;
  if (!user) return null;
  return <UserProfileCard user={user} />;
}

Cache con Map en el servicio

Una promesa por usuario 

// Map: una promesa por usuario para reutilizarla y evitar duplicados.
const userPromises = new Map<number, Promise<User>>();

interface JsonPlaceholderUser {
  id: number;
  name: string;
}

// toUser: normaliza la respuesta y genera el avatar.
const toUser = (data: JsonPlaceholderUser): User => ({
  id: String(data.id),
  name: data.name,
  avatar: `https://api.dicebear.com/9.x/initials/svg?seed=${data.name}`,
});

const fetchUser = async (id: number): Promise<User> => {
  const response = await fetch(`${USERS_API_URL}/${id}`);

  if (!response.ok) {
    throw new Error(`Usuario ${id} no encontrado`);
  }

  const data: JsonPlaceholderUser = await response.json();
  return toUser(data);
};

const getById = (id: number): Promise<User> => {
  const cached = userPromises.get(id);
  if (cached) return cached;

  // Si falla, la promesa queda en el Map para que React reciba
  // siempre el mismo error y no repita la petición.
  const promise = fetchUser(id);
  userPromises.set(id, promise);
  return promise;
};

const refetch = (id: number): Promise<User> => {
  userPromises.delete(id);
  return getById(id);
};

// Después de actualizar un usuario:
// userPromises.delete(id);
Importante: el Map vive en el servicio, así que la misma promesa se comparte entre componentes y sobrevive a los remounts. Si el fetch falla, la promesa se mantiene en el Map para evitar un loop de peticiones. refetch(id) elimina la entrada y fuerza un nuevo intento. Después de updateName, también se elimina la entrada para evitar datos viejos.

🔄 Hook useTransition

⏳ Actualizaciones no urgentes

useTransition marca una actualización como no urgente. React puede interrumpirla si el usuario sigue interactuando. No hace la API más rápida: mantiene la interfaz disponible mientras el guardado ocurre en segundo plano.

const handleSubmit = (e) => {

  startTransition(async () => {

<Input ... /> // ✅ no se deshabilita
Diferencia: en React 18 lazy() suspende mientras carga el chunk y useEffect carga los datos con un spinner interno. En React 19 use() suspende directamente mientras espera la promesa del usuario, así que el fallback de Suspense cubre la carga inicial. En el guardado, React 18 bloquea el formulario con isSaving; React 19 mantiene el input disponible y usa isPending.

⚡ Hook useOptimistic

💬 UI inmediata mientras la acción termina

useOptimistic muestra un valor temporal mientras una acción está en curso. Cuando la acción termina, React reconcilia ese valor con el estado real.

React 18: el comentario aparece al terminar la API

React 18 

import { useState } from "react";

const [isSaving, setIsSaving] = useState(false);
const [error, setError] = useState<Error | null>(null);

const handleSubmit = async (e) => {
  e.preventDefault();
  const text = form.text.trim();
  if (!text) return;

  setIsSaving(true);
  setError(null);

  try {
    const saved = await commentsApi.addComment(text);
    setComments((prev) => [...prev, saved]);
    updateForm({ text: "" });
  } catch (err) {
    setError(new Error(getErrorMessage(err, "Error al guardar el comentario")));
  } finally {
    setIsSaving(false);
  }
};

// El ErrorBoundary del componente padre captura este throw.
if (error) throw error;

React 19: useOptimistic + useTransition

React 19 

import { useOptimistic, useTransition } from "react";

const [isPending, startTransition] = useTransition();
const [optimisticComments, addOptimisticComment] = useOptimistic(
  comments,
  (current, newComment) => [
    ...current,
    { ...newComment, pending: true },
  ],
);

const handleSubmit = (e) => {
  e.preventDefault();
  const text = form.text.trim();
  if (!text) return;

  updateForm({ text: "" });

  startTransition(async () => {
    addOptimisticComment({ id: crypto.randomUUID(), text });

    const saved = await commentsApi.addComment(text);

    startTransition(() => {
      setComments((prev) => [...prev, saved]);
    });
  });
};
Diferencia: el comentario optimista es temporal. Se muestra con “Enviando...” y se reemplaza por el comentario confirmado cuando responde la API. La actualización optimista debe ejecutarse dentro de una acción o transición. Ambas versiones están envueltas en un ErrorBoundary: React 18 guarda el error y lo relanza en el render; React 19 lo propaga desde la transición.

React 19: useActionState + useFormStatus

React 19 

// version-19/LoginFormContent.tsx (extracto)
import { useActionState } from "react";
import { useFormStatus } from "react-dom";

interface LoginState {
  error?: string;
  success?: string;
}

async function loginAction(
  _prevState: LoginState | null,
  formData: FormData,
): Promise<LoginState> {
  const emailEntry = formData.get("email");
  const passwordEntry = formData.get("password");
  const email = typeof emailEntry === "string" ? emailEntry : "";
  const password = typeof passwordEntry === "string" ? passwordEntry : "";
  const result = await authApi.login({ email, password });

  if (result.success) {
    return { success: result.message };
  }
  return { error: result.message };
}

function SubmitButton() {
  const { pending, data } = useFormStatus();
  const email = data?.get("email");

  return (
    <>
      <FormSubmitButton
        isPending={pending}
        idleText="Iniciar sesión"
        pendingText="Autenticando..."
      />
      {pending && email && (
        <p className="col-12 small text-muted mt-1 mb-0">
          Enviando {String(email)}...
        </p>
      )}
    </>
  );
}

export function LoginFormContent() {
  const [state, formAction] = useActionState(loginAction, null);

  return (
    <Form action={formAction} title="Iniciar sesión">
      <Input label="Email" name="email" type="email" required />
      <Input label="Contraseña" name="password" type="password" required />
      {state?.error && (
        <Alert variant="danger" className="col-12 py-2">
          {state.error}
        </Alert>
      )}
      {state?.success && (
        <Alert variant="success" className="col-12 py-2">
          {state.success}
        </Alert>
      )}
      <SubmitButton />
    </Form>
  );
}

En el proyecto, version-18/LoginForm.tsx y version-19/LoginForm.tsx envuelven el contenido con ErrorBoundary.

¿Cuándo usar cada uno?

  • useActionState: estado del resultado de la action, validación, errores y mensajes de éxito.
  • useFormStatus: pending y data del formulario, leído desde un componente hijo como el botón de envío.
Importante: los errores esperados se devuelven como estado; los errores inesperados se lanzan y los captura el ErrorBoundary.

El componente


import type { ButtonHTMLAttributes, PropsWithChildren } from "react";
import { colorMapper } from "./constants/colorMapper";
import type { ButtonColor } from "./types";

interface ButtonProps
  extends
    Omit<ButtonHTMLAttributes<HTMLButtonElement>, "color">,
    PropsWithChildren {
  text?: string;
  color?: ButtonColor;
}

export const Button = ({
  text,
  type = "button",
  color = "primary",
  className,
  children,
  ...rest
}: ButtonProps) => {
  return (
    <button
      type={type}
      className={`btn ${colorMapper[color]} ${className ?? ""}`}
      {...rest}
    >
      {children ?? text}
    </button>
  );
};

El test


import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { Button } from "../../../src/components/button/Button";

describe("Button", () => {
  it("renderiza el texto pasado por la prop `text`", () => {
    render(<Button text="Guardar" />);

    expect(screen.getByRole("button", { name: "Guardar" })).toBeInTheDocument();
  });

  it("renderiza `children` y los prioriza sobre `text`", () => {
    render(
      <Button text="Guardar">
        <span>Enviar</span>
      </Button>,
    );

    expect(screen.getByRole("button", { name: "Enviar" })).toBeInTheDocument();
    expect(
      screen.queryByRole("button", { name: "Guardar" }),
    ).not.toBeInTheDocument();
  });

  it("aplica la clase por defecto `btn btn-primary` cuando no se pasa color", () => {
    render(<Button text="Aceptar" />);

    const button = screen.getByRole("button", { name: "Aceptar" });
    expect(button).toHaveClass("btn", "btn-primary");
  });

  it("aplica la clase mapeada según el color y conserva `className` extra", () => {
    render(<Button text="Eliminar" color="danger" className="me-2" />);

    const button = screen.getByRole("button", { name: "Eliminar" });
    expect(button).toHaveClass("btn", "btn-danger", "me-2");
  });

  it('usa `type="button"` por defecto para no enviar formularios', () => {
    render(<Button text="Enviar" />);

    const button = screen.getByRole("button", { name: "Enviar" });
    expect(button).toHaveAttribute("type", "button");
  });

  it("permite sobreescribir el `type` (ej. submit)", () => {
    render(<Button text="Enviar" type="submit" />);

    const button = screen.getByRole("button", { name: "Enviar" });
    expect(button).toHaveAttribute("type", "submit");
  });

  it("dispara `onClick` cuando el usuario hace clic", async () => {
    const user = userEvent.setup();
    const onClick = jest.fn();

    render(<Button text="Incrementar" onClick={onClick} />);
    await user.click(screen.getByRole("button", { name: "Incrementar" }));

    expect(onClick).toHaveBeenCalledTimes(1);
  });

  it("propaga atributos nativos del <button> (disabled, aria-label)", () => {
    render(<Button text="Cargando" disabled aria-label="Botón de carga" />);

    const button = screen.getByRole("button", { name: "Botón de carga" });
    expect(button).toBeDisabled();
  });
});

Recordatorio: getBy* falla si no encuentra el elemento; queryBy* devuelve null y es útil para comprobar que algo no existe. userEvent simula la interacción real.

🧱 Estructura del proyecto

🗂️ Cómo está organizado el demo

El proyecto se ejecuta con una sola versión de React (React 19). Las carpetas version-18 y version-19 no cambian el runtime: contienen los patrones “antes” y “ahora” que se comparan en cada pestaña.

  • version-18 / version-19: componentes específicos de cada patrón. Los archivos no llevan sufijo; el alias se define al importarlos desde el demo padre.
  • ReactVersionProvider: guarda la versión seleccionada de forma global y la persiste en localStorage con la clave digitalers-react-version.
  • DemoTabs: mantiene el estado de la pestaña activa para que el header y el provider no se re-rendericen al cambiar de tab.
  • DemoCard: muestra el toggle de versión y renderiza el contenido seleccionado.
  • ErrorBoundary: se divide en ErrorBoundary.tsx (mensaje + Alert) y ErrorBoundaryComponent.tsx (boundary de clase).
  • components: componentes compartidos como Button, Form, Input, Spinner y Alert.

Las diferencias de cada pestaña son de patrón de código, no de versión instalada de React.
